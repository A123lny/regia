# Cantiere F0 — Fondamenta della piattaforma Regìa (locale)

> **Per agenti esecutori:** SUB-SKILL RICHIESTA — usare `superpowers:subagent-driven-development` (raccomandato) o `superpowers:executing-plans` per implementare questo piano un task alla volta. Gli step usano checkbox `- [ ]` per il tracciamento.

**Obiettivo:** Aprire il cantiere F0 della piattaforma Regìa in ambiente locale — repo riordinato, scaffolding Next.js/TS strict, Supabase locale via CLI, modello dati canonico (RN-87), autenticazione minimale, audit log, controlli RS-1/RS-8 in una "CI locale" (`npm run ci`), backup e ripristino provati.

**Architettura:** Monolite modulare TypeScript (§9.1). Un'unica app Next.js in `app/`, con moduli M1–M13 come cartelle isolate sotto `app/src/modules/*/` esposte solo dal loro `public.ts` (RS-1). Persistenza in Supabase (Postgres + pgvector + Auth + Storage) avviata in locale via Supabase CLI + Docker (RS-8). Nessuna coda in F0 (BullMQ arriva con F2). Nessuna chiamata AI in F0.

**Tech stack:**
- Linguaggio: TypeScript strict end-to-end
- Web: Next.js 15 (App Router) con `src/` directory
- Database: Supabase locale (Postgres 15 + pgvector nativo) via `supabase` CLI
- Test: Vitest (unit/logic) + `pgTAP` opzionale per invarianti SQL (o test SQL via `supabase db test`)
- Lint boundaries: `dependency-cruiser` (RS-1)
- Formattazione: Prettier
- Node package manager: npm (già installato, versione 10.9.2)

## Retrospettiva post-esecuzione (8 set 2026)

Errori e deviazioni rilevati durante l'esecuzione dei 10 task. Non modificano i dettagli dei task originari — servono come lens per rileggere il piano e non ripetere gli stessi errori nei piani successivi.

1. **Typo tsconfig:** il piano scriveva `noPropertyAccessFromIndexSignatures` (plurale) — il flag corretto è `noPropertyAccessFromIndexSignature` (singolare). Corretto in loco al Task 2.
2. **Naming migrazioni:** la convenzione del piano (`YYYYMMDD_NNNNNN_name.sql`) causa collisione version-key in Supabase CLI v2.116. Il formato corretto è `YYYYMMDDNNNNNN_name.sql` (14 cifre continue, nessun underscore nel prefisso numerico). Tutte le migrazioni rinominate al Task 5.
3. **Porte reali su questa macchina:** Hyper-V riserva le porte 54315–54414. Porte effettive: API 54520, DB 54521, Studio 54522. Qualsiasi script che usa 54321/54322/54323 va adattato.
4. **`pg_dump`/`psql` non su PATH:** usare `docker exec supabase_db_app pg_dump` per il dump e `docker exec -i supabase_db_app psql` per il ripristino. La CLI `npx supabase db dump --local` non produce dump combinato schema+dati.
5. **Alias `@/*` in Next 16 con `--src-dir`:** l'alias mappa a `./src/*`, quindi il path corretto è `@/lib/...` e non `@/src/lib/...`. Il piano ai Task 6–7 citava path con `@/src/`.
6. **`ON CONFLICT (email)` su `auth.users` non funziona:** il campo email non ha un constraint unique esplicito su questa versione di Supabase. Soluzione usata in `dev-create-owner.sh`: Admin REST API (`/auth/v1/admin/users`).
7. **RLS abilitata su tutte le tabelle F0 con denial-by-default:** aggiunta al Task 5 fix (migrazione `000007`). Il commento nel piano al Task 6 "in F0 non ci sono RLS" è **falso** — aggiornare i riferimenti in F1.
8. **Doppio `dotenv` rimosso da `ci.sh`:** il piano al Task 5 suggeriva `set -a; source .env.local` prima di `npm test` in ci.sh, ma `npm test` usa già `dotenv-cli`. Il doppio caricamento creava conflitti; rimosso al Task 5 fix round.
9. **Sequenza commit reale:** 22 commit totali (10 task + 6 fix round aggiuntivi: task 2 fix, task 4 pooler fix, task 5 security fix, task 6 fix, task 7 fix, task 8 fix, task 9 fix, task 9 review fix), non 10 come previsto originariamente. Pianificare fix round nel tempo stimato dei task futuri.

-- RF-11.3: audit log consultabile, filtrabile, esportabile, IMMUTABILE.
-- Ogni azione umana e dell'agente vi finisce.
-- RA-8.12: per ogni azione dell'agente conserviamo origine, contesto, motivo,
-- strumenti, esito, costo (nei details JSONB).
-- RS-3: l'invariante "append-only" è enforced in DB via trigger, non solo in codice.

create table public.audit_events (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references public.organizations(id) on delete restrict,
  actor_user_id uuid null references auth.users(id) on delete set null,
  actor_kind text not null check (actor_kind in ('user', 'agent', 'system')),
  action text not null check (length(action) between 1 and 200),
  target text null check (target is null or length(target) between 1 and 500),
  details jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);

create index audit_events_org_created_idx
  on public.audit_events(organization_id, created_at desc);
create index audit_events_actor_idx
  on public.audit_events(actor_user_id, created_at desc)
  where actor_user_id is not null;
create index audit_events_action_idx
  on public.audit_events(action);

-- Blocco a livello DB di UPDATE e DELETE.
-- Chiunque usi il service_role vede questi trigger scattare: nemmeno un errore
-- in codice può cancellare la traccia.
create or replace function public.deny_audit_events_mutation()
returns trigger language plpgsql as $$
begin
  raise exception 'audit_events is append-only (RF-11.3)';
end;
$$;

create trigger audit_events_no_update
  before update on public.audit_events
  for each row execute function public.deny_audit_events_mutation();

create trigger audit_events_no_delete
  before delete on public.audit_events
  for each row execute function public.deny_audit_events_mutation();

comment on table public.audit_events is
  'RF-11.3: audit log immutabile. Nessuna UPDATE/DELETE consentita.';

# RQ-5: ripristino da dump. Distruttivo: droppa lo schema public e ricrea da dump.
# NON usare su altro che il DB locale.

if [ $# -ne 1 ]; then
  echo "Uso: $0 <path-al-dump.sql>" >&2
  exit 2
fi

DUMP="$1"
if [ ! -f "${DUMP}" ]; then
  echo "File non trovato: ${DUMP}" >&2
  exit 2
fi

if [ "${CONFIRM}" != "SI" ]; then
  echo "Annullato."
  exit 1
fi

echo "==> Drop schemi"
psql "${DB_URL}" <<'SQL'
drop schema if exists public cascade;
